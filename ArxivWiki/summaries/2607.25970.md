# Reinforcement Learning for Code Optimization

arXiv: [2607.25970](https://arxiv.org/pdf/2607.25970v1) &middot; Published 2026-07-28 &middot; Recommendation: **Read later** (score 15/25)

## High-Level Summary

Extends reinforcement learning from code correctness to code speed. Naively adding execution time to the reward fails -- timing noise and reward sparsity swamp the signal, producing barely-faster code and more failures. Fixing the measurement harness, the reward composition, and the training procedure together lifted strict top-50% pass@1 from 18.0% to 31.3% on a 7B model and 30.7% to 50.4% on a 32B.

## Key Highlights

- The reported failure mode is the useful part: a noisy reward channel has to be engineered before it can be learned from, and the naive version actively degrades correctness.
- Three separable pieces -- a calibrated timing sandbox, a composed correctness-and-speed reward tuned offline before training, and RL adjusted for the sparser signal.
- Gains grow at stricter thresholds, with 125% relative improvement at top-30% for the larger model, and pure-correctness scores are preserved rather than traded away.
- Measured against the fastest correct human submissions: about half the human rate of complexity-class improvements, so the honest claim is constant-factor speedups, not algorithmic insight.

## Why It Matters for Enterprise AI

Coding assistants are sold on developer throughput; this points at compute spend instead, where the savings are measurable on an infrastructure bill. The transferable engineering lesson is broader than code: if you want to optimise against a noisy measured quantity -- latency, cost, conversion -- the measurement harness is the prerequisite, and skipping it makes the whole effort fail in a way that looks like the model's fault. The human comparison is also a useful expectation-setter for anyone being pitched AI-driven performance work.

## Business Applications

- Target AI code optimisation at hot paths where compute cost is measurable, and expect constant-factor gains rather than better algorithms.
- Build and calibrate the timing or cost measurement harness before attempting any optimisation-reward training, as the largest single determinant of success.
- Keep a correctness gate alongside any speed objective, since the naive reward design degraded correctness while chasing latency.
